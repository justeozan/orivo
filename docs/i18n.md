# Interface languages

All interface text goes through `t()` from `src/i18n.ts`:

```ts
import { t } from "./i18n";
`<strong>${t("settings.startPage.label")}</strong>`
t("library.count", { count: 3 }) // "{count} games" → "3 games"
```

- **English is the source.** Add every new key to the `en` catalogue first; its
  keys are the `MessageKey` type, so a typo in `t("…")` fails `pnpm typecheck`.
- **Other languages are partial.** A missing key falls back to English, so a
  translation can land screen by screen.
- **The language is settled before render.** It is remembered in
  `localStorage` (`orivo.language`) and in the host preferences; a change
  reloads the page. Strings computed at import time (e.g. `SETTINGS_SECTIONS`)
  can therefore call `t()` directly.

## Adding a language

1. `src/i18n.ts`: add the code to `LANGUAGES`, its own name to
   `LANGUAGE_NAMES`, a catalogue to `CATALOGUES`.
2. `src-tauri/src/preferences.rs`: add the variant to `enum Language`.

## Where messages live

`src/locales/<area>.ts`, one `en` and one `fr` export each, merged in
`src/i18n.ts`; keys are prefixed by area (`app.`, `detail.`, `runners.`,
`store.`, `me.`, `misc.`). `src/i18n.test.ts` fails if a language lacks a key.

Deliberately not translated: brand and game names, messages coming from the
Rust host, demo/sample data (`mock-library.ts`, the browser-only fallbacks in
`game-detail-model.ts`), and the generated store catalogue
(`store-catalog.generated.ts`, French editorial copy built by `scripts/`).
